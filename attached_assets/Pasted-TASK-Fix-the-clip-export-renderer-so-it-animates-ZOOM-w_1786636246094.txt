BACKGROUND (verified by log analysis of a real export, clip id 2437):
- ffmpegExport.ts currently builds one crop filter where w/h are frozen from the FIRST keyframe (rawFrameW/rawFrameH from keyframe[0]) and only x/y are animated via a nested if() expression chain.
- Because zoom changes are discarded, positions saved for a small zoomed-in frame get replayed with a large frame, pushing the crop outside the video — the pad step then fills the overflow with black. This is the confirmed cause of the black-space bug (observed: pad=3930:1404 on a 3840x1080 source).
- MAX_CROP_KEYFRAMES = 30 exists only because the nested if() expression breaks past ~30 branches. A real user path had 558 keyframes reduced to 30, which smears fast pans. The client-side preview (applyFrameToVideo) interpolates the full path linearly per animation frame — export must match that behavior.

REQUIRED APPROACH:
1. Replace the nested if() expression mechanism with FFmpeg's sendcmd filter driving a crop filter, reading commands from a generated temp file:
   - Generate a command file with one entry per output frame time (interpolate the stored keyframe path linearly, exactly like applyFrameToVideo does client-side).
   - Each entry sets crop w, h, x, y for that timestamp (crop supports w/h/x/y as runtime commands).
   - Filter chain becomes: [pad if needed],sendcmd=f=<cmdfile>,crop@dyn=<w0>:<h0>:<x0>:<y0>,scale=1920:1080:force_original_aspect_ratio=disable
   - The scale step normalizes the varying crop sizes to the fixed output, so the encoder always sees constant dimensions.
2. Per-keyframe pixel math: w_px = w*SRC_W, h_px = h*SRC_H per keyframe (NOT from keyframe[0] only). Round w/h to even numbers. Clamp x,y so the crop stays inside the padded canvas.

4. Remove the 30-point downsampling for the render path (MAX_CROP_KEYFRAMES). If you want a safety ceiling on the command file size, cap at one command per output frame (that is already the natural density).

7. Keep sanitizeKeyframes' validation, but make sure it no longer rewrites or drops keyframes solely because h doesn't match the first frame's aspect-derived height — h varies with w by design (h = w * srcAspect / outAspect).
